# Product Requirements Document (PRD)
## منصة إلكترونية لحجز ملاعب البادل (Padel Booking Platform)

**الإصدار:** 1.0
**الحالة:** Draft
**آخر تحديث:** 2026-07-31

---

## 1. نظرة عامة (Overview)

منصة ويب/تطبيق ثنائية اللغة (عربي / إنجليزي) لحجز ملاعب البادل، دون الحاجة لإنشاء حساب من طرف العميل، مع لوحة تحكم كاملة للإدارة.

المشروع مقدَّم كجزء من المرحلة الثانية (الاختبار العملي) لبرنامج نهج للتدريب المقرون بالتوظيف، ويُقيَّم على أساس: جودة الكود، هيكلة المشروع، تصميم قاعدة البيانات، جودة الـ API، الأمان، الأداء، واجهة المستخدم، والتفكير البرمجي في التعامل مع منطق الحجز والتسعير.

**الموعد النهائي للتسليم:** الاثنين 2026/08/03 الساعة 4:00 عصرًا.

---

## 2. المشكلة (Problem Statement)

أصحاب ملاعب البادل يديرون الحجوزات يدويًا (اتصال هاتفي / واتساب)، ما يسبب:
- تعارض الحجوزات (Double booking).
- عدم وضوح الأسعار والعروض للعميل.
- عدم وجود سجل مركزي للحجوزات والمدفوعات.
- تجربة بطيئة للعميل الذي يريد حجز سريع بدون تسجيل.

## 3. الهدف (Goal)

بناء نظام متكامل (Backend + Frontend) يسمح لـ:
1. **الإدارة**: التحكم الكامل بالملاعب، الأسعار، العروض، والحجوزات.
2. **العميل**: حجز ساعة ملعب متاحة خلال دقائق، بدون تسجيل حساب.

---

## 4. المستخدمون (User Personas)

| الشخصية | الوصف | الاحتياج الأساسي |
|---|---|---|
| **مدير المنشأة (Admin)** | يدير الملاعب والأسعار ويراقب الحجوزات | لوحة تحكم شاملة وسريعة |
| **العميل (Customer)** | يريد حجز ملعب بادل لوقت معيّن | تجربة حجز سريعة بدون عوائق |

## 5. المتطلبات الوظيفية (Functional Requirements)

### 5.1 لوحة التحكم (Admin Dashboard)

| # | المتطلب | التفاصيل |
|---|---|---|
| A1 | إدارة الملاعب | إضافة / تعديل / حذف عدد غير محدود من الملاعب |
| A2 | ساعات العمل | تحديد ساعات عمل كل ملعب بشكل مستقل |
| A3 | إغلاق الملاعب | إغلاق ملعب واحد / عدة ملاعب / جميع الملاعب، في أيام أو تواريخ محددة |
| A4 | التسعير | تحديد سعر الساعة الواحدة لكل ملعب |
| A5 | العروض الترويجية | إنشاء عروض تعتمد على عدد الساعات (مثال: ساعة = 10 ريال، ساعتان = 8 ريال لكل ساعة) |
| A6 | عرض الحجوزات | فلترة حسب: الملعب، التاريخ، حالة الحجز، طريقة الدفع، رقم هاتف العميل |
| A7 | تسجيل الدخول | Authentication آمن للوحة التحكم (JWT) |

### 5.2 واجهة العميل (Customer Interface)

| # | المتطلب | التفاصيل |
|---|---|---|
| C1 | بدون تسجيل | لا يتطلب إنشاء حساب |
| C2 | البيانات المطلوبة | رقم الهاتف **إجباري**، الاسم والبريد الإلكتروني **اختياريان** |
| C3 | اختيار الموعد | اختيار التاريخ ثم عرض الأوقات المتاحة فقط |
| C4 | حجز متعدد | إمكانية حجز أكثر من ساعة، وأكثر من يوم، ضمن نفس العملية (سلة حجز) |
| C5 | إخفاء اسم الملعب | لا يُعرض اسم/هوية الملعب للعميل إطلاقًا |
| C6 | العرض الديناميكي للتوفر | إذا كان هناك 3 ملاعب متاحة لنفس الوقت، يبقى الوقت "متاحًا" حتى تُستنفد كل الملاعب الثلاثة |
| C7 | التخصيص العشوائي | عند تأكيد الحجز، يخصّص النظام ملعبًا متاحًا بشكل عشوائي (Randomized court assignment) |
| C8 | منع الحجز غير الصالح | يُمنع حجز أوقات ماضية، أو فترات مغلقة/غير متاحة |
| C9 | طرق الدفع | الدفع عند الوصول، أو الدفع الإلكتروني عبر بوابة **Thawani** (Sandbox) |

## 6. المتطلبات غير الوظيفية (Non-Functional Requirements)

- **الاستجابة (Responsive):** يعمل بسلاسة على الموبايل، التابلت، وسطح المكتب.
- **إمكانية الوصول (Accessibility):** اتباع أساسيات WCAG.
- **الأمان:** تشفير كلمات المرور، حماية من SQL Injection/XSS/CSRF، حماية Endpoints الإدارية بـ JWT.
- **الأداء:** استجابة API أقل من 300ms للعمليات القياسية؛ فهرسة قاعدة البيانات بشكل صحيح.
- **قابلية التوسع:** بنية طبقية (Layered/Clean Architecture) تسمح بإضافة ميزات لاحقًا (منشآت متعددة، أنواع ملاعب أخرى...).
- **الدعم ثنائي اللغة:** عربي (RTL) وإنجليزي (LTR) مع تبديل فوري بدون إعادة تحميل الصفحة.
- **العملة والمنطقة الزمنية:** OMR / Asia/Muscat.
- **التوافق:** Chrome, Safari, Edge, Firefox.

## 7. خارج النطاق (Out of Scope — للنسخة الأولى)

- تطبيقات الجوال الأصلية (Native iOS/Android) — يُكتفى بويب متجاوب أو Flutter حسب اختيار الفريق.
- نظام ولاء / نقاط للعملاء.
- دعم منشآت متعددة (Multi-tenant) — يمكن اعتبارها ميزة تفاضلية مستقبلية.
- إشعارات SMS فعلية (تُبنى البنية لدعمها لاحقًا فقط إن اتسع الوقت).

---

## 8. مقاييس النجاح (Success Criteria)

- إتمام عملية حجز كاملة (اختيار تاريخ → وقت → دفع → تأكيد) في أقل من دقيقتين.
- عدم حدوث أي تعارض حجوزات (double booking) تحت أي ظرف.
- تغطية 100% من المتطلبات الوظيفية المذكورة في وثيقة الاختبار الأصلية.
- كود نظيف قابل للتشغيل من أول محاولة باتباع خطوات README.

---

## 9. ميزات تفاضلية مقترحة (Nice-to-Have / Differentiators)

هذه ليست مطلوبة في وثيقة الاختبار لكنها تُظهر عمق فهم وجودة تنفيذ:

- Timeline تفاعلي لعرض الحجوزات.
- تقويم إداري بسحب وإفلات (Drag & Drop) لإدارة الحجوزات.
- تحديثات توفر شبه لحظية (Polling أو WebSocket خفيف).
- رمز مرجعي للحجز (Booking Reference Code) + QR Code للتأكيد.
- لوحة تحليلات (نسبة إشغال، الإيرادات).
- سجل تدقيق (Audit Log) للعمليات الإدارية.
- إشعارات Toast، وحالات Skeleton Loading، وتحديثات متفائلة (Optimistic UI).
- دعم PWA.
