# Engineering Plan — خطة التنفيذ
## منصة حجز ملاعب البادل

**المهلة الزمنية الكلية:** حتى 2026/08/03 الساعة 4:00 عصرًا.

> ملاحظة من وثيقة الاختبار: **جودة التنفيذ أهم من كثرة الميزات** — نظام مكتمل بدقة أفضل من نظام كبير غير مكتمل. الخطة أدناه مبنية على هذا المبدأ: أولوية قصوى للمتطلبات الأساسية (Core)، ثم التحسينات فقط إن تبقّى وقت.

---

## المرحلة 0 — الإعداد (Setup) — ~2 ساعات
- [ ] إنشاء المستودع (public repo) بهيكلة `backend/`, `frontend/`, `database/`, `docs/`.
- [ ] إعداد ASP.NET Core 8 solution بالطبقات الأربع (Api/Application/Domain/Infrastructure).
- [ ] إعداد مشروع React + Vite + TypeScript + Tailwind + shadcn/ui.
- [ ] إعداد MySQL (Docker Compose) + أول Migration فارغة للتأكد من الاتصال.
- [ ] إعداد Git، `.gitignore`، `.env.example`.

## المرحلة 1 — الأساس (Domain + Database) — ~3 ساعات
- [ ] بناء الكيانات (Entities) في `Padel.Domain` طبقًا لـ `04-Backend-Schema.md`.
- [ ] EF Core Configurations + Migrations لكل الجداول.
- [ ] Seed data: مدير افتراضي، 3–4 ملاعب تجريبية، عرض تسعير تجريبي.

## المرحلة 2 — Backend Core (Authentication + Courts) — ~3 ساعات
- [ ] `/api/auth/login` (JWT).
- [ ] CRUD كامل `/api/admin/courts` + `court_schedules`.
- [ ] `/api/admin/closures` (إغلاق ملعب/عدة/الكل، تاريخ أو مدى).
- [ ] Middleware للتحقق من JWT + معالجة الأخطاء الموحدة.

## المرحلة 3 — محرك الحجز (Booking Engine) — ~5 ساعات (الأهم)
- [ ] `GET /api/customer/availability` — حساب السلوتات المتاحة (بدون كشف أسماء الملاعب).
- [ ] منطق التسعير والعروض (`PricingService`).
- [ ] `POST /api/customer/book` — Transaction ذرّية + تخصيص عشوائي للملعب + قفل لمنع Race Condition.
- [ ] توليد `booking_reference` فريد.
- [ ] Unit Tests لمنطق التخصيص العشوائي ومنع التعارض (أولوية عالية — هذا ما سيُختبر عمليًا).

## المرحلة 4 — الدفع (Payment) — ~2 ساعات
- [ ] تكامل Thawani Sandbox (Checkout Session Creation).
- [ ] Webhook استقبال حالة الدفع + تحديث `payments`/`bookings`.
- [ ] مسار "الدفع عند الوصول" (بدون بوابة).

## المرحلة 5 — لوحة التحكم (Admin Frontend) — ~4 ساعات
- [ ] Login page.
- [ ] Dashboard (ملخص سريع: حجوزات اليوم، إيرادات).
- [ ] صفحة الملاعب (CRUD + ساعات العمل).
- [ ] صفحة الإغلاقات.
- [ ] صفحة الحجوزات (جدول + فلاتر).
- [ ] صفحة العروض/التسعير.

## المرحلة 6 — واجهة العميل (Customer Frontend) — ~4 ساعات
- [ ] Landing + اختيار اللغة.
- [ ] اختيار التاريخ + عرض الأوقات المتاحة (Time Slot Grid).
- [ ] سلة الحجز (دعم أكثر من ساعة/يوم).
- [ ] نموذج بيانات العميل + طريقة الدفع.
- [ ] صفحة التأكيد.
- [ ] i18n كامل (عربي/إنجليزي) + RTL.

## المرحلة 7 — الجودة (QA) — ~2 ساعات
- [ ] اختبار سيناريوهات التعارض (حجزين متزامنين لنفس السلوت).
- [ ] اختبار الحواف: حجز وقت ماضٍ، حجز فترة مغلقة، امتلاء كل الملاعب.
- [ ] مراجعة الاستجابة (Responsive) على أحجام شاشات مختلفة.
- [ ] مراجعة الكود (Linting: ESLint + dotnet format).

## المرحلة 8 — التسليم (Delivery) — ~1 ساعة
- [ ] كتابة `README.md` شامل (خطوات تشغيل، تقنيات، بيانات دخول لوحة التحكم، ملاحظات).
- [ ] (اختياري لكن مفضّل) رفع Demo على خادم تجريبي.
- [ ] رفع المستودع كـ Public repository.
- [ ] التسليم عبر لوحة التحكم في صفحة الطلب قبل 2026/08/03 4:00 عصرًا.
